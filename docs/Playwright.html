01

Setup & the two CLIs you'll use

Playwright ships two entry points: the test runner (@playwright/test) for your specs, and the Playwright CLI (playwright) for codegen, browser installs, and one-off launches. 

# Install the test runner + CLI, then download browser binaries (one shot)
$ npm init playwright@latest # scaffolds config, example specs, installs browsers
# If Playwright is already in the repo, just fetch the browsers
$ npx playwright install chromium # pulls only Chromium; drop the name for all engines
// A minimal spec so you can see the shape of a test
import { test, expect } from '@playwright/test'; // runner + assertions

test('sandbox home loads', async ({ page }) => { // page = fresh browser tab
await page.goto('https://my-sandbox.sandbox.my.salesforce.com'); // open the org
await expect(page).toHaveTitle(/Salesforce/); // assert the tab title
});
Rule of thumb — use npx playwright ... for anything interactive (recording, launching, showing reports) and npx playwright test for running specs in CI or locally.
02

Writing tests: locators, actions & assertions

A test is three steps on repeat: go somewhere, find + do something, check something happened. Everything below is the vocabulary for those three steps.

Anatomy of one test

import { test, expect } from '@playwright/test';

test('creates a new case', async ({ page }) => { // one test = one async function
await page.goto('/lightning/o/Case/list'); // 1. go
await page.getByRole('button', { name: 'New' }).click(); // 2. find + do
await expect(page.getByText('Case: New Case')).toBeVisible(); // 3. check
});
# Run just this one spec file
$ npx playwright test tests/case-flow.spec.ts

Locators — how you point at Lightning elements

Locator Example Why / when
getByRole page.getByRole('button', { name: 'Save' }) First choice — matches what a user actually sees, survives markup changes.
getByLabel page.getByLabel('Subject') Great for record-detail form fields with a visible label.
getByText page.getByText('Case Number') Plain text/labels that aren't inside a form control.
getByTestId page.getByTestId('case-save-btn') Rock solid, but needs a data-testid added to the LWC markup.
CSS (locator) page.locator('.slds-spinner') Last resort — Lightning regenerates class hashes across releases.
Salesforce tip — reach for role/label/text locators before CSS. Lightning's generated class names are not stable between orgs or releases.

Actions — the ones you'll use daily

await page.getByLabel('Subject').fill('Cannot log in'); // type into a field
await page.getByLabel('Status').selectOption('Working'); // picklist
await page.getByLabel('Escalated').check(); // checkbox on
await page.getByLabel('Attachment').setInputFiles('screenshot.png'); // upload a file
await page.getByRole('button', { name: 'Save' }).click(); // submit
Action Purpose
click() / hover() / focus() Click, hover over, or focus an element.
fill() Clear a field and type a value into it.
check() / uncheck() Set a checkbox to on/off.
press() Press a single key, e.g. 'Enter' or 'Escape'.
selectOption() Choose an option from a <select>/picklist.
setInputFiles() Upload one or more files to a file input.

Assertions — checks that auto-retry until they pass

expect() keeps re-checking the condition until it's true or the timeout runs out, so you don't need a wait before it. 

await expect(page).toHaveTitle(/Salesforce/); // tab title
await expect(page.getByText('Case Number')).toBeVisible(); // element showed up
await expect(page.getByLabel('Subject')).toHaveValue('Cannot log in'); // field value
Matcher Checks
toBeVisible() / toBeEnabled() / toBeChecked() Element state.
toContainText() / toHaveText() Text content, partial or exact.
toHaveValue() Current value of an input/picklist.
toHaveCount() Number of matching elements (e.g. rows in a related list).
toHaveURL() / toHaveTitle() Current page URL / tab title.

Grouping tests & hooks

import { test, expect } from '@playwright/test';

test.describe('Case management', () => { // groups related tests together
test.beforeEach(async ({ page }) => { // runs before EVERY test in this group
await page.goto('/lightning/o/Case/list');
});

test('creates a case', async ({ page }) => { /* ... */ });
test('closes a case', async ({ page }) => { /* ... */ });
});
# Run only tests inside that describe block, by its title
$ npx playwright test -g "Case management"
Test isolation — every test gets a brand-new page and browser context — "equivalent to a brand new browser profile." Nothing (cookies, local storage) leaks between tests unless you deliberately load a saved storageState (sections 04/06/13) or a persistent profile (section 06).
03

Recording with codegen: basics & flags

codegen opens a browser, watches you click around, and writes the locators/actions for you. Section 04 shows it wired up with a saved Salesforce login — this is the plain version and the flags that go with it.

Bare minimum

# URL is optional — type it into the window that opens if you leave it off
$ npx playwright codegen my-sandbox.sandbox.my.salesforce.com

Click around normally; the recorder writes Playwright code live in a second window. Use its Pick Locator button to hover any element (great for Lightning's deeply nested DOM) and get a robust locator without recording a click.

Flags worth knowing

Flag What it does
-o, --output=<file> Write the generated code straight to a file instead of the preview pane.
--target=<lang> Language/flavour of the generated code: playwright-test (default — a full spec with test(...)), javascript (a plain script with chromium.launch()), python, python-pytest, java, csharp...
-b, --browser=<engine> Which engine to record in: chromium (default), firefox, webkit. Independent of --channel.
--test-id-attribute=data-qa Tells the recorder which attribute counts as a test id, so it emits getByTestId() instead of a brittle CSS chain. Set it to whatever your LWCs use.
--timeout=<ms> Per-operation timeout for the recorder's own navigations (default 180000).
--device="iPhone 13" Emulate a device preset (viewport + user agent + touch).
--viewport-size="1440,900" Custom window size instead of a device preset.
--color-scheme=dark Force light/dark mode — handy for testing an SLDS dark theme.
--geolocation="41.89,12.49" Fake GPS coordinates.
--lang=en-US Force the browser's language.
--timezone="Asia/Kolkata" Force the browser's timezone.
--user-agent="..." Override the UA string the browser sends.
--save-storage=auth.json After you log in, save cookies/local storage to a JSON file.
--load-storage=auth.json Start the recorder already logged in, using a file saved above.
--save-har=net.har / --save-har-glob="**/api/**" Record every request into a HAR file (optionally only URLs matching the glob) so you can replay or mock that traffic later with page.routeFromHAR().
--ignore-https-errors Accept self-signed/inspected certificates — needed behind some corporate TLS proxies.
--proxy-server=http://host:8080 / --proxy-bypass=".corp,localhost" Route the recorded browser through a proxy, with an optional no-proxy list.
--block-service-workers Stop service workers from registering. Useful when a cached Lightning service worker serves stale assets mid-recording.
--channel=chrome / --user-data-dir=<path> Use a real/reusable Chrome profile instead of bundled Chromium — see sections 05-06.
Where these flags come from — most of them are just CLI spellings of the same context options you can set in playwright.config.ts under use (section 10). --channel, --user-data-dir and --proxy-server map to launch options instead (section 09). 
# A few flags combined: dark mode, US English, and save the login for reuse
$ npx playwright codegen --color-scheme=dark --lang=en-US --save-storage=auth.json https://my-sandbox.sandbox.my.salesforce.com
Prefer clicking buttons? — the "Playwright Test for VS Code" extension adds a Record new button in the Testing sidebar that does the exact same thing without touching the terminal.
04

Codegen recipes for logged-in sessions

Plain codegen starts from a blank temp profile, so you meet the login page and MFA every single time. These are the ways to record inside an already-authenticated Salesforce session — pick the one that matches how long you need the session to live.

Recipe Session lives in Reach for it when
A — save/load storage state One JSON file Default choice. Same file feeds storageState in your config.
B — persistent profile dir A Chrome profile folder You need extensions, or MFA "remember this device" to stick.
C — attach to running Chrome The browser you already have open You're mid-investigation in an org and want to record from here.
D — pause inside a test The test's own context Extending a spec that already logs itself in (section 07).

Recipe A — record the login once, replay it forever

# Step 1: log in by hand (incl. MFA), then CLOSE the window — cookies + localStorage land in auth.json
$ npx playwright codegen --save-storage=.auth/sf-state.json https://test.salesforce.com
# Step 2: every later recording starts INSIDE the org, and writes a real spec file
#   --load-storage       restore that saved session (no login page)
#   --target             emit a test(...) block instead of a bare script
#   --test-id-attribute  prefer getByTestId over CSS when the attribute exists
#   --viewport-size      record at the size CI will run at
#   -o                   write straight into the repo
$ npx playwright codegen --load-storage=.auth/sf-state.json --target=playwright-test --test-id-attribute=data-qa --viewport-size="1440,900" -o tests/case-flow.spec.ts https://my-sandbox.sandbox.my.salesforce.com/lightning/o/Case/list

That same .auth/sf-state.json is exactly what use: { storageState: '.auth/sf-state.json' } loads at run time — record and run share one session artifact.

Recipe B — record inside the persistent profile

# --user-data-dir keeps the whole profile (cookies, MFA device trust, extensions) on disk
$ npx playwright codegen --channel=chrome --user-data-dir=./.auth/sf-profile -o tests/new-flow.spec.ts https://my-sandbox.sandbox.my.salesforce.com

--channel=chrome swaps bundled Chromium for the Chrome you actually have installed; --user-data-dir is what makes the session survive between runs. Full setup in section 06.

Recipe C — attach the recorder to a Chrome you already have open

The CLI can't attach to a live browser, but a five-line script can: connectOverCDP joins the running Chrome, and page.pause() opens the Inspector with its Record button — so you're recording in a tab that's already logged in, with your extensions and history intact. 

# 1. Start Chrome with a debugging port (quit all other Chrome windows first)
$ "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --remote-debugging-port=9222 --user-data-dir=./.auth/sf-profile
# Windows: "C:\Program Files\Google\Chrome\Application\chrome.exe" --remote-debugging-port=9222 --user-data-dir=C:\pw-profile
import { chromium } from 'playwright';

const browser = await chromium.connectOverCDP('http://localhost:9222'); // join, don't launch
const ctx = browser.contexts()[0]; // the profile's existing context (already logged in)
const page = ctx.pages()[0] ?? await ctx.newPage(); // grab the open tab
await page.pause(); // Inspector opens -> hit Record and click around
# PWDEBUG=1 makes sure the Inspector window actually appears
$ PWDEBUG=1 node attach.mjs
CDP caveat — when you connect over CDP, Playwright did not start the browser, so launchOptions (headless, args, slowMo, channel…) are ignored — the flags on the chrome.exe command line are the only ones that count.

Recipe D — record the network, then replay it offline

# Capture only Salesforce's Aura/UI-API calls while you click through the flow
$ npx playwright codegen --load-storage=.auth/sf-state.json --save-har=.har/case.har --save-har-glob="**/{aura,services/data}/**" https://my-sandbox.sandbox.my.salesforce.com
// Serve those recorded responses instead of hitting the org — fast, deterministic UI tests
await page.routeFromHAR('.har/case.har', {
  url: '**/{aura,services/data}/**', // only intercept what you captured
  update: false, // true = re-record the HAR on this run instead of replaying
  notFound: 'abort', // 'fallback' would let un-recorded calls hit the real org
});

Other one-off launchers

# open = same browser as codegen, minus the recorder — a quick authenticated poke at the org
$ npx playwright open --load-storage=.auth/sf-state.json https://my-sandbox.sandbox.my.salesforce.com

# Emulate a device while recording (viewport + UA + touch in one flag)
$ npx playwright codegen --device="iPhone 14" --load-storage=.auth/sf-state.json https://my-sandbox.sandbox.my.salesforce.com

# Headless one-shot artifacts — handy for a bug report
$ npx playwright screenshot --full-page --load-storage=.auth/sf-state.json "https://…/lightning/o/Case/list" case-list.png
$ npx playwright pdf "https://…/apex/MyVisualforcePage" page.pdf
Sessions expire — a saved storage state is only as good as the org's session timeout (often 2h–8h) and dies on password reset or an admin session kill. When a "logged-in" run suddenly lands on the login page, re-run the Recipe A step-1 command. Keep .auth/ and *.har out of Git — both contain live tokens.
05

Launch Chrome with your real (main) profile

Reuse your everyday Chrome — saved passwords, MFA-trusted device, and live Salesforce sessions all come along. This is a fast way to poke at an org without logging in again.

The one-liner (fastest)

# Point codegen at your OS Chrome profile dir; --channel=chrome uses installed Chrome, not bundled Chromium
$ npx playwright codegen --channel=chrome --user-data-dir="$HOME/Library/Application Support/Google/Chrome" https://login.salesforce.com
Heads-up — Chrome refuses to open a profile that another Chrome window already holds open. Fully quit Chrome first, or you'll get a "profile in use" / lock error.

Profile directory by OS

OS Default Chrome user-data-dir
macOS ~/Library/Application Support/Google/Chrome
Windows %LOCALAPPDATA%\Google\Chrome\User Data
Linux ~/.config/google-chrome

Same thing in JS

import { chromium } from 'playwright'; // core lib, not the test runner

// launchPersistentContext keeps cookies/sessions on disk; '' would be a temp dir,
// so we pass the REAL Chrome data dir to inherit logins.
const ctx = await chromium.launchPersistentContext(
process.env.HOME + '/Library/Application Support/Google/Chrome', // user-data-dir
{
channel: 'chrome', // use system Chrome (has your extensions + profile)
headless: false, // you want to SEE it
args: ['--profile-directory=Default'], // pick which profile ("Default", "Profile 1"...)
}
);
const page = await ctx.newPage(); // already-authenticated tab
await page.goto('https://my-sandbox.sandbox.my.salesforce.com');
Warning — automating your primary profile can dirty your real history/cookies and is riskier if a script misbehaves. For repeatable work, prefer the dedicated test profile in the next section.
06

A reusable, persistent test profile

Create a throwaway profile folder once, log into your sandbox once, and every future launch pointed at that folder starts already logged in. This is the pattern you'll use daily.

Step 1 — create the profile & log in (interactive, one time)

# Fresh empty dir becomes a brand-new profile; log into the sandbox by hand this once
$ npx playwright codegen --channel=chrome --user-data-dir=./.auth/sf-profile https://test.salesforce.com

Log in fully (including MFA). When you close the window, the session cookies are written into ./.auth/sf-profile.

Step 2 — relaunch anytime, already authenticated

# Same dir = same cookies; you land inside the sandbox with no login prompt
$ npx playwright open --channel=chrome --user-data-dir=./.auth/sf-profile https://my-sandbox.sandbox.my.salesforce.com

The reusable JS helper

import { chromium } from 'playwright';

// Reusable launcher: any script that imports this gets the SAME logged-in profile.
export async function openSandbox() {
const ctx = await chromium.launchPersistentContext(
'./.auth/sf-profile', // dedicated dir -> sessions survive between runs
{ channel: 'chrome', headless: false }
);
// Reuse the tab Chrome already opened instead of spawning a blank one
const page = ctx.pages()[0] ?? await ctx.newPage();
await page.goto('https://my-sandbox.sandbox.my.salesforce.com'); // no login needed
return { ctx, page };
}
Cleaner alternative — instead of a whole profile folder, you can save just the auth state to a single JSON file with page.context().storageState({ path: 'auth.json' }) after logging in, then load it per test with use: { storageState: 'auth.json' }. Lighter, and Git-ignorable. Add both .auth/ and auth.json to .gitignore — they contain live session tokens.
07

Can you edit code while recording?

Short answer: the codegen recorder window is read-only — you can't type into that generated-code pane. But there are two clean ways to get editable code out of a live session.

Option A — record, then paste & edit

Use the recorder's toolbar to copy the generated script (choose your language from the dropdown), then paste into your editor and edit freely. You can also record straight to a file: 

# -o writes the generated test to a file you then open in your IDE to edit
$ npx playwright codegen -o tests/case-flow.spec.ts --channel=chrome --user-data-dir=./.auth/sf-profile https://my-sandbox.sandbox.my.salesforce.com

Option B — pause inside a running test and record live

This is the real "edit while recording" experience. Drop page.pause() into a spec; the Inspector opens with Record and Explore buttons. Your existing code keeps running, and new actions you perform are generated live — which you then copy into your file. 

import { test } from '@playwright/test';

test('author a case comment', async ({ page }) => {
await page.goto('/lightning/o/Case/list'); // baseURL from config is prepended
await page.pause(); // <-- opens Inspector; press Record and click around to generate more steps
// ...continue writing assertions using the locators the Inspector suggests
});
# PWDEBUG=1 forces the Inspector open for the whole run (implicit pause at start)
$ PWDEBUG=1 npx playwright test tests/case-flow.spec.ts
Best of both — the Explore button in the Inspector lets you hover any element to get a robust locator without recording a click — great for Salesforce's deeply nested Lightning DOM.
08

Running tests: paths, filters & modes

Beyond plain npx playwright test, the runner takes a path, a title, a line number, or a browser/project — and can be combined with any profile technique from sections 04-07, or the profile-backed project defined in section 13.

Run one file (pass the path)

# Just this spec file, whatever browser/project the config defaults to
$ npx playwright test tests/case-flow.spec.ts
# Same file, but run it against the authenticated sf-authed project (section 13)
$ npx playwright test tests/case-flow.spec.ts --project=sf-authed

Run a folder, or match by filename keyword

# Every spec inside these two folders
$ npx playwright test tests/case-flow/ tests/lead-flow/
# Any spec file whose name contains "case" or "lead" — no path needed
$ npx playwright test case lead --project=sf-authed

Run one test by its title

# -g filters by test title (regex-aware) instead of file name
$ npx playwright test -g "create a new case" --project=sf-authed

Run the exact test at a line number

# Jump straight to the test starting at line 42 and step through it
$ npx playwright test tests/case-flow.spec.ts:42 --debug

Pick the browser — or your saved profile project

# --project also selects a real engine when your config defines one
$ npx playwright test --project webkit
# Run the same suite against more than one engine in a single command
$ npx playwright test --project webkit --project firefox

Config-wide: point the runner at a profile

// playwright.config.ts — a project that always uses the persistent profile
import { defineConfig } from '@playwright/test';

export default defineConfig({
projects: [{
name: 'sf-authed',
use: {
channel: 'chrome', // system Chrome
headless: false, // watch it drive the org
// launchPersistentContext isn't set directly here; use storageState instead:
storageState: './.auth/sf-state.json', // cookies saved in section 04/06
baseURL: process.env.SF_URL, // so goto('/lightning/...') works
},
}],
});

Per-run: choose the profile with an env var

# Swap which profile/URL a run uses without touching code — pick test vs main here
$ SF_URL=https://my-sandbox.sandbox.my.salesforce.com npx playwright test --project=sf-authed

Full manual control (persistent profile inside a test)

import { test } from '@playwright/test';
import { chromium } from 'playwright';

// When you truly need the on-disk profile (not just storageState):
test('runs in the sf-profile', async () => {
const profile = process.env.PROFILE ?? './.auth/sf-profile'; // choose at run time
const ctx = await chromium.launchPersistentContext(profile, { channel: 'chrome' });
const page = await ctx.newPage();
await page.goto('/lightning/setup/SetupOneHome/home');
await ctx.close();
});
# Pick the profile at launch: main Chrome profile vs your test profile
$ PROFILE="$HOME/Library/Application Support/Google/Chrome" npx playwright test

Headed, UI mode & Debug mode — three ways to watch it run

Flag What you get
--headed A real visible browser window (the default is headless — no window at all).
--ui Interactive UI mode: watch, time-travel, and pick locators for every test.
--debug Opens the Inspector and pauses before the first action, so you can step through. 
# Headed run against your authenticated profile project
$ npx playwright test --headed --project=sf-authed
# UI mode — usually the fastest way to author/debug a whole file
$ npx playwright test --ui
# Debug just one file, stepping through it in the Inspector
$ npx playwright test tests/case-flow.spec.ts --debug

Re-run just what failed

# Only re-runs the tests that failed last time — fast feedback after a fix
$ npx playwright test --last-failed --project=sf-authed

The rest of the runner flags

Flag What it does
--list Print the tests that would run and exit — the safe way to check a filter.
--workers=1 Run serially. Do this when several tests touch the same Salesforce record and trip over each other, or when one licensed user can't hold parallel sessions.
--repeat-each=10 Run each selected test N times — the flakiness detector.
--retries=2 Override the config's retry count for this run only.
-x / --max-failures=3 Stop after the first (or Nth) failure instead of grinding through the suite.
--grep-invert="@slow" The opposite of -g — skip everything matching. Pairs well with @tags in test titles.
--only-changed=master Run only specs changed versus that git ref — a cheap pre-push smoke run.
--shard=1/3 Split the suite across 3 CI machines; merge later with merge-reports.
--trace=on / --video=on / --screenshot=on Force capture for this run even if the config only captures on failure.
--reporter=line,html Override reporters for one run (comma-separated).
--timeout=90000 / --global-timeout=1800000 Per-test budget / hard ceiling for the whole run.
--config=playwright.uat.ts Point at a different config — the clean way to keep per-org settings apart.
--update-snapshots Accept current output as the new baseline for visual/snapshot assertions. 
# Flakiness hunt: one worker, no retries, same test 10x, stop at the first red
$ npx playwright test -g "create a new case" --repeat-each=10 --retries=0 --workers=1 -x --trace=on

Env vars that change a run

Variable Effect
PWDEBUG=1 Opens the Inspector, forces headed, and disables timeouts so you can poke around freely.
PWDEBUG=console Headed run with the playwright object exposed in DevTools console — try locators live against the real Lightning page.
DEBUG=pw:api Logs every Playwright call and what it waited for — best tool for "why did this hang?".
CI=1 Flips the process.env.CI branches in your config (retries, workers, forbidOnly).
PLAYWRIGHT_BROWSERS_PATH Where browser binaries live — set it when a locked-down machine can't write to the default cache. 
# Windows PowerShell sets env vars differently than bash
$ $env:PWDEBUG="1"; npx playwright test tests/case-flow.spec.ts # PowerShell
$ PWDEBUG=1 npx playwright test tests/case-flow.spec.ts # bash / zsh / Git Bash
09

launchOptions — controlling the browser process

Everything so far configured the page. launchOptions configures the browser executable Playwright starts: which binary, which command-line switches, how it's sandboxed, where downloads go. Set it once in use and every test inherits it. 

// playwright.config.ts — launchOptions sits INSIDE use, next to the context options
import { defineConfig } from '@playwright/test';

export default defineConfig({
use: {
channel: 'chrome', // which Chrome build (also a launch option, hoisted for convenience)
headless: false, // same deal — hoisted out of launchOptions

    launchOptions: {
      slowMo: 300,                // pause 300ms after EVERY action — watch the flow, catch mis-clicks
      timeout: 60_000,            // how long to wait for the browser process itself to boot (0 = forever)
      downloadsPath: './downloads', // where accepted downloads (report exports) are written
      tracesDir: './traces',       // raw trace scratch dir
      env: { LANG: 'en_US.UTF-8' }, // env vars handed to the browser process
      chromiumSandbox: false,      // required inside most Docker/CI containers

      args: [                       // raw Chromium switches — see the table below
        '--start-maximized',
        '--disable-dev-shm-usage',
        '--disable-blink-features=AutomationControlled',
      ],
      ignoreDefaultArgs: ['--hide-scrollbars'], // drop a switch Playwright normally passes
    },

    viewport: null, // REQUIRED for --start-maximized to actually fill the screen

},
});

Every launch option, and when you'd touch it

Option What it does
headless true = no window (fast, CI default). false = a real window you can watch. Some SSO/IdP flows behave differently headless — if a login works headed but not headless, this is your first suspect.
channel Use an installed browser build instead of bundled Chromium: 'chrome', 'chrome-beta', 'msedge', 'msedge-beta', 'chromium'. Matches what your users run.
executablePath Absolute path to a specific binary — for a locked corporate Chrome install or a pinned version on a build agent. Overrides channel.
args Extra command-line switches passed straight to the browser (table below).
ignoreDefaultArgs true drops all of Playwright's default switches (rarely what you want); an array drops just the listed ones, e.g. to keep the "Chrome is being controlled by automated software" infobar.
slowMo Milliseconds to wait after each operation. Demo/debug only — never commit it enabled.
timeout Budget for the browser to start (default 30 s). Raise it on slow/loaded VMs; 0 disables.
proxy { server, bypass, username, password } — route traffic through a corporate proxy. bypass is a comma-separated no-proxy list.
downloadsPath Directory for downloaded files. Without it, downloads go to a temp dir that's deleted when the browser closes — the usual reason a report-export assertion can't find its file.
tracesDir Where raw traces are staged before being zipped into the test output.
env Environment variables for the browser process (locale, proxy vars, custom flags).
chromiumSandbox Set false in containers that can't grant the sandbox its privileges — the supported alternative to sprinkling --no-sandbox.
handleSIGINT / handleSIGTERM / handleSIGHUP Whether the browser closes when the node process is signalled. Turn off if you want the window to survive a Ctrl-C.
firefoxUserPrefs Firefox-only about:config preferences, as a key/value object.
devtools Chromium-only: auto-open DevTools for each tab. Deprecated — prefer --debug/UI mode.

Chromium args worth knowing

Switch Why you'd add it
--start-maximized Fill the screen. Only works with viewport: null, otherwise Playwright resizes the page back.
--window-size=1920,1080 / --window-position=0,0 Deterministic window geometry — useful on multi-monitor machines and for screenshots.
--disable-dev-shm-usage Docker's tiny /dev/shm crashes Chrome on heavy Lightning pages; this moves shared memory to disk. Standard in CI.
--no-sandbox Same job as chromiumSandbox: false. Only in a trusted container.
--disable-gpu Avoids GPU-driver flakiness on headless CI agents.
--disable-blink-features=AutomationControlled Removes the navigator.webdriver tell — helps when a login page or bot filter behaves differently for automation.
--disable-notifications / --disable-popup-blocking Kills the Chrome notification prompt; lets Salesforce's "open in new window" actions through.
--auto-open-devtools-for-tabs DevTools open on every new tab — handy while chasing a console error in an LWC.
--remote-debugging-port=9222 Exposes CDP so another tool (or the attach recipe in section 04) can join the browser.
--disable-extensions-except=<dir> + --load-extension=<dir> Load an unpacked extension (e.g. Salesforce Inspector Reloaded). Needs a persistent context and headed mode.
--force-device-scale-factor=1 / --font-render-hinting=none Makes screenshots byte-stable across machines — pair with visual comparisons.
--lang=en-US Browser UI language; set locale (section 10) too, since that's what the page actually reads.

The same options outside the test runner

import { chromium } from 'playwright';

// chromium.launch() takes launch options directly — this is the object `launchOptions` mirrors
const browser = await chromium.launch({
channel: 'chrome',
headless: false,
slowMo: 200,
args: ['--start-maximized'],
proxy: { server: 'http://proxy.corp:8080', bypass: '.internal,localhost' },
});

// launchPersistentContext() takes launch AND context options in ONE object,
// because the profile dir IS the context — no separate browser.newContext() step.
const ctx = await chromium.launchPersistentContext('./.auth/sf-profile', {
channel: 'chrome', // launch option
args: ['--start-maximized'], // launch option
viewport: null, // context option
locale: 'en-US', // context option
acceptDownloads: true, // context option
});
When launchOptions is ignored — if you connect to a browser you didn't start (connectOverCDP, connect, or a remote grid), the process already exists, so args, headless, channel and friends do nothing. slowMo is the one exception — it's applied client-side.

Context & emulation options in use

The other half of use: options handed to the browser context — the isolated profile each test gets. Identity, network, emulation, and artifacts all live here, and every one of them can be overridden per project, per file, or per test.

Identity & navigation

Option What it does
baseURL Prefix for relative page.goto('/lightning/...'). One env var swaps the whole suite to another org.
storageState Cookies + localStorage to start with — a path or an inline object. This is what skips login.
httpCredentials { username, password } for HTTP basic auth prompts (some sandbox front doors and staging proxies).
extraHTTPHeaders Headers added to every request — e.g. a bypass token for a WAF sitting in front of the org.
ignoreHTTPSErrors Accept invalid certs. Needed when a TLS-inspecting proxy re-signs Salesforce traffic.
proxy Per-context proxy, overriding the launch-level one.
offline Cuts network for the context — test your offline/error states.
serviceWorkers 'allow' (default) or 'block'. Block them when a stale worker serves old Lightning assets or swallows your route mocks.

Emulation — make every machine agree

Option What it does
viewport { width, height } of the page. null means "use the real window" — required for --start-maximized.
deviceScaleFactor Pixel density. 2 gives retina-sized screenshots.
isMobile / hasTouch Enable the mobile meta-viewport and touch events — Salesforce serves a different Lightning shell to touch devices.
userAgent Override the UA string.
locale e.g. 'en-US', 'de-DE' — drives Accept-Language plus number/date formatting. Test that your date assertions aren't locale-dependent.
timezoneId 'Asia/Kolkata', 'America/Los_Angeles'… essential when asserting on CreatedDate-style timestamps.
geolocation + permissions Fake coordinates; you must also grant ['geolocation'] or the page never gets them.
colorScheme / reducedMotion / forcedColors Drive the matching CSS media queries. reducedMotion: 'reduce' also kills SLDS animations, which quietly reduces flake.
javaScriptEnabled / bypassCSP Turn JS off (rarely useful for Lightning), or bypass Content-Security-Policy so injected scripts run.
acceptDownloads Default true; keep it on to assert on report/list-view exports.
testIdAttribute Which attribute getByTestId() reads — set it to your LWC convention, e.g. 'data-qa'.
contextOptions Escape hatch: raw options passed to browser.newContext() that have no dedicated use key.

Artifacts & timeouts

Option Values
trace 'off', 'on', 'retain-on-failure', 'on-first-retry', 'on-all-retries'.
screenshot 'off', 'on', 'only-on-failure'.
video 'off', 'on', 'retain-on-failure', 'on-first-retry'.

Overriding per file or per test

import { test, expect } from '@playwright/test';

// Applies to every test in this file — merged over the config's `use`
test.use({ timezoneId: 'Asia/Kolkata', locale: 'en-IN', viewport: { width: 1280, height: 720 } });

test.describe('guest checkout on the community', () => {
test.use({ storageState: { cookies: [], origins: [] } }); // deliberately logged OUT for this group

test('shows the login prompt', async ({ page }) => {
await page.goto('/s/');
await expect(page.getByRole('button', { name: 'Log In' })).toBeVisible();
});
});
Precedence, highest first — CLI flag → test.use() in a describe → test.use() in a file → project use → top-level use → Playwright's default. When an option "isn't taking effect", something further up this list is winning.

Manual breaks & time-based pauses

Two different needs: a manual break to inspect state and step through, and a timed pause to wait out an animation or a slow Lightning redraw. Use the right one — avoid hard waits in real specs.

Manual break — stop and take over

await page.pause(); // halts the script, opens Inspector; resume/step with its buttons
# Run in headed + debug so page.pause() and stepping actually surface a UI
$ npx playwright test --headed --debug

Timed pause — wait a fixed duration

// waitForTimeout is a HARD wait — fine for debugging/demos, avoid in committed tests
await page.waitForTimeout(3000); // pause 3s (3000 ms) regardless of page state
Why avoid hard waits — a fixed 3s is either too short (flaky) or too long (slow). Prefer waiting for a condition (section 12). Reserve waitForTimeout for throwaway debugging.

Slow the whole run down to watch it

// slowMo adds a delay AFTER every action so you can follow along visually
const browser = await chromium.launch({ headless: false, slowMo: 500 }); // 500ms between steps
# Env-driven slow motion for a full test run without editing code
$ PWSLOWMO=500 npx playwright test --headed # (read PWSLOWMO in your config's launchOptions)
// The config side of that env var (see section 09 for the rest of launchOptions)
use: { launchOptions: { slowMo: Number(process.env.PWSLOWMO ?? 0) } }, // 0 = full speed
12

Keep waiting until a component appears

Salesforce Lightning renders lazily — spinners, lazy tabs, streaming lists. Playwright's auto-waiting handles most of it, but for stubborn cases you poll until the element exists or a condition is true.

Built-in auto-wait (prefer this)

// Actions auto-wait up to the timeout for the element to be visible & actionable
await page.getByRole('button', { name: 'New' }).click({ timeout: 30000 }); // waits ≤30s

// Explicitly wait for a locator to become visible before asserting
await expect(page.getByText('Case Number')).toBeVisible({ timeout: 30000 });

Wait for a selector to attach/appear

// waitForSelector polls the DOM until the element hits the requested state
await page.waitForSelector('lightning-datatable', {
  state: 'visible',  // 'attached' | 'visible' | 'hidden' | 'detached'
  timeout: 60000,   // give slow orgs up to 60s
});

Poll a custom condition (true "keep looking" loop)

// expect.poll re-runs the function on an interval until it passes or times out —
// ideal when "loaded" means a count/state, not just one element existing.
await expect.poll(async () => {
  return await page.locator('tbody tr').count(); // how many rows rendered so far
}, {
  timeout: 60000,   // keep polling up to 60s
  intervals: [500, 1000, 2000], // back-off: 0.5s, 1s, then every 2s
}).toBeGreaterThan(0);  // condition: at least one row is present

// Or wait on a page-side JS predicate (e.g., a spinner gone)
await page.waitForFunction(() =>
!document.querySelector('.slds-spinner') // true once the spinner leaves the DOM
, null, { timeout: 60000 });
# Raise the global action/expect timeout for an entire slow-org run
$ npx playwright test --timeout=90000 # 90s per test before it's marked failed
Salesforce tip — the classic spinner selector is .slds-spinner; waiting for it to detach after a save is far more reliable than a fixed waitForTimeout. Also prefer role/label locators over CSS — Lightning regenerates class hashes.

The login project that produces the session

This is the automated version of section 04's recipe A: instead of recording the login by hand, a tiny "test" logs in once per run and saves the state every other project then loads. 

// tests/global.setup.ts — runs first because other projects list it in `dependencies`
import { test as setup, expect } from '@playwright/test';

const STATE = './.auth/sf-state.json';

setup('authenticate', async ({ page }) => {
await page.goto(process.env.SF_URL!); // login host, e.g. https://test.salesforce.com
await page.getByLabel('Username').fill(process.env.SF_USER!); // credentials from env, never in Git
await page.getByLabel('Password').fill(process.env.SF_PASS!);
await page.getByRole('button', { name: 'Log In' }).click();

// Wait for a post-login marker BEFORE saving, or you persist a half-finished session
await expect(page).toHaveURL(/lightning/, { timeout: 60_000 });
await page.context().storageState({ path: STATE }); // the file every other project loads
});
# One command: logs in, then runs the suite with that fresh session
$ SF_URL=https://test.salesforce.com SF_USER=qa@org.com.sandbox SF_PASS='…' npx playwright test --project=chromium-authed
MFA — this only works for a user who can log in without an interactive second factor: an IP-relaxed profile/trusted network range, or a login-flow exemption for the integration user. If your QA user is hard-MFA'd, stay on the hand-recorded storage state (section 04) or the persistent profile (section 06), where the device trust cookie survives.

The options you'll actually touch, ranked

Option Why it matters for Salesforce
timeout / expect.timeout Lightning is slow; too-low values are your #1 source of false failures.
trace The single best debugging feature — a time-travel snapshot of DOM + network + console.
storageState Skips the login+MFA dance on every test. Set once, reuse everywhere.
baseURL Lets specs use relative paths; swap orgs by changing one env var.
retries Absorbs genuine platform flakiness in CI without hiding real bugs (keep at 0 locally).
channel 'chrome' matches what users actually run and plays nicer with Salesforce than bundled Chromium.
projects Separate a one-time login project from your test projects; choose at runtime with --project.
launchOptions The browser process itself — args for container stability, slowMo for demos, downloadsPath for export assertions. Section 09.
locale / timezoneId Pins formatting and clock so a suite that passes in Chandigarh also passes on a US-East build agent.
